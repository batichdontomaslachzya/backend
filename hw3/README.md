# Image Service — HW1–HW4

HTTP-сервис на Go: регистрация, загрузка PNG/JPEG, асинхронная обработка четырьмя
фильтрами и получение исходника или результата через API. Пользователи и задачи
хранятся в PostgreSQL, сессии — в Redis, задания передаются через Kafka.
Prometheus собирает метрики, Grafana показывает готовый дашборд.

## Запуск

Нужны Docker Desktop с Linux-контейнерами и Python 3. Из корня репозитория
перейдите в каталог проекта командой `cd hw3`, затем выполните:

```sh
python scripts/setup_env.py
docker compose up -d --build --wait --wait-timeout 240
```

Скрипт добавляет недостающие случайные секреты в `.env`, сохраняя существующие.
Этот файл исключён из Git и Docker build context. Не меняйте пароль PostgreSQL
в `.env` после создания тома: смена требует отдельной команды в самой БД.
Пароль администратора Grafana из окружения также применяется при первом запуске.

- API: http://127.0.0.1:8000
- OpenAPI: http://127.0.0.1:8000/openapi.yaml
- Grafana: http://127.0.0.1:3000/d/image-service — логин `admin`, пароль в `.env`, поле `GRAFANA_PASSWORD`.
- Prometheus: http://127.0.0.1:9090

Swagger UI и пользовательский веб-интерфейс не включены; API можно вызывать через
curl, PowerShell или Postman. Порты опубликованы только на localhost.
Другой порт API задаётся через `HTTP_PORT` в `.env`.

```sh
docker compose ps
docker compose logs --tail=100 -f
docker compose stop
docker compose start
docker compose down
```

`down` сохраняет именованные тома; `down -v` удаляет данные, поэтому для обычной
остановки он не нужен. Для перехода с запущенного HW3 сначала выполните
`docker compose -p image-service-hw3 down` без `-v`. У файлов и Kafka явно сохранены
прежние имена томов. Старые пользователи и задачи HW3 были только в RAM и не могут
автоматически восстановиться в PostgreSQL. Начиная с HW4 новые записи сохраняются.

## Семь сервисов

| Сервис | Роль и данные |
| --- | --- |
| api | Go HTTP-сервер, авторизация, SQL, загрузка/выдача файлов, публикация задач |
| processor | Go-процесс: Kafka → фильтр → PNG → callback |
| postgres | Пользователи, хеши паролей, задачи, фильтр, состояние публикации |
| redis | Хеш токена → user_id, TTL 24 часа; AOF и отдельный том |
| kafka | Один брокер в KRaft, топик image-tasks, группа image-processor |
| prometheus | Сбор метрик каждые 5 секунд, хранение 7 дней |
| grafana | Автоматически настроенные источник Prometheus и дашборд |

API и processor используют общий том `images`: `/data/input/<id>.image` и
`/data/result/<id>.png`. В Kafka отправляется только ID и описание фильтра.
В БД находятся метаданные и относительные пути, сами картинки остаются файлами.
Redis используется как быстрое хранилище сессий; кэш копий изображений не добавлялся.

## Пример: от регистрации до картинки

В PowerShell, после запуска Compose:

```powershell
$base = 'http://127.0.0.1:8000'
$body = @{ username = 'student'; password = 'learning-password' } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "$base/register" -ContentType 'application/json' -Body $body
$login = Invoke-RestMethod -Method Post -Uri "$base/login" -ContentType 'application/json' -Body $body
$headers = @{ Authorization = "Bearer $($login.token)" }
$filterPath = Join-Path $env:TEMP 'image-filter.json'
[IO.File]::WriteAllText($filterPath, '{"name":"blur","parameters":{"sigma":1.2}}')
$response = curl.exe -s -X POST "$base/task" -H "Authorization: Bearer $($login.token)" -F "image=@C:/Pictures/example.png" -F "filter=<$filterPath"
$task = $response | ConvertFrom-Json
Invoke-RestMethod "$base/status/$($task.task_id)" -Headers $headers
```

Замените путь к изображению на свой. Когда статус станет `ready`:

```powershell
Invoke-WebRequest "$base/image/$($task.task_id)" -Headers $headers -OutFile original.png
Invoke-WebRequest "$base/result/$($task.task_id)" -Headers $headers -OutFile result.png
```

Исходник возвращается без изменения байтов. Для JPEG укажите расширение `.jpg`.
Результат всегда PNG. Повторная регистрация занятого логина даёт `409`; можно сразу войти.
В браузере картинка отображается, если запрос передаёт Bearer-токен; обычная навигация
по ссылке без заголовка вернёт `401`. API не передаёт токен в URL.

## API

Регистрация, вход и правила паролей остались прежними: JSON `username/password`,
логин 3-32 латинские буквы/цифры/`_`, пароль 8-128 байт, тело до 4096 байт.
Пароли хешируются PBKDF2-HMAC-SHA256 с солью и 600 000 итераций.
Сессия действует 24 часа, хранится на сервере, токен не является JWT.

| Маршрут | Ответ |
| --- | --- |
| `POST /register` | `201`: user_id, username; занятый логин - `409` |
| `POST /login` | `200`: token; неверные данные - `401` |
| `POST /task` | multipart: image + filter; `201`: task_id |
| `GET /status/{task_id}` | `200`: in_progress, ready или failed; при failed есть error |
| `GET /image/{task_id}` | `200`: исходный PNG/JPEG |
| `GET /result/{task_id}` | `200`: PNG; `202`: ещё не готово; `422`: задача завершилась ошибкой |
| `POST /commit` | служебный callback, отдельный секрет; успех/повтор - `204` |
| `GET /healthz` | `200`: HTTP-процесс работает; это не проверка зависимостей |
| `GET /metrics` | `200`: метрики Prometheus |
| `GET /openapi.yaml` | публичная спецификация |

Все маршруты картинок и задач требуют `Authorization: Bearer <user-token>`.
Без действующей сессии - `401`, чужая или неизвестная задача - `404`.
JSON и картинки не кэшируются клиентом (`Cache-Control: no-store`).

Для загрузки требуется ровно один файл `image` и одно текстовое поле `filter`
с JSON. Имя файла клиента не используется как путь на диске.
Формат определяется из содержимого, а не имени или MIME, указанного клиентом.

Лимиты: 10 MiB на файл, 11 MiB на запрос, максимум 4096 по каждой стороне
и 8 миллионов пикселей. Неправильные данные дают `400`, превышение размера - `413`.
API проверяет заголовок изображения, обработчик повторяет проверку размеров
и декодирует весь файл. Повреждённые пиксельные данные переводят задачу в `failed`.

### Фильтры

| filter | Действие |
| --- | --- |
| `{"name":"negative"}` | Инверсия RGB, прозрачность сохраняется |
| `{"name":"flip_x"}` | Отражение относительно горизонтальной оси: верх и низ меняются местами |
| `{"name":"blur","parameters":{"sigma":1.2}}` | Гауссово размытие |
| `{"name":"sharpen","parameters":{"sigma":1.2}}` | Повышение резкости |

Для blur/sharpen требуется `0 < sigma <= 10`. Для двух простых фильтров sigma
не нужен. Негатив и отражение реализованы вручную, blur/sharpen используют `imaging`.

## Сохранение и обработка

1. Middleware находит сессию в Redis и передаёт user_id обработчику.
2. API проверяет файл/фильтр, сохраняет исходник и вставляет задачу в PostgreSQL.
3. `201` означает, что задача сохранена. Поле `published_at = NULL` означает,
   что её ещё нужно отправить. Диспетчер API читает такие строки и публикует в Kafka.
4. Только после подтверждения Kafka диспетчер записывает `published_at`.
5. Processor читает сообщение, декодирует файл, применяет фильтр, записывает PNG
   через временный файл и rename, затем вызывает служебный `/commit`.
6. API меняет статус на ready/failed в SQL. Первый терминальный статус сохраняется.
7. Processor подтверждает Kafka offset только после успешного callback.

Строка задачи одновременно играет роль outbox — сохранённого намерения отправить
сообщение. Поэтому отдельная таблица и универсальный фреймворк очередей не нужны.
При недоступной Kafka уже запущенный API продолжает принимать задачи; диспетчер
повторяет публикацию. При своём запуске API сначала проверяет все зависимости.
После рестарта он снова читает неопубликованные строки. Один диспетчер рассчитан
на один экземпляр API; доставка допускает повторы, а не exactly-once.

Сбой между подтверждением Kafka и отметкой в SQL может вызвать повторную обработку.
Callback идемпотентен: `UPDATE ... WHERE status = 'in_progress'` не меняет уже
завершённую задачу. При временном отказе callback worker повторяет запрос без ACK.
`404` от callback означает отсутствующую задачу; такое старое сообщение пропускается.

PostgreSQL хранит пользователей и задачи между рестартами. Redis сохраняет сессии
через AOF, срок жизни не продлевается при чтении. Истёкшая сессия — `401`, недоступный
Redis или PostgreSQL — `503`. AOF everysec допускает потерю примерно последней
секунды записей при аварии питания; тома не заменяют резервные копии.

## Миграция и структура

`migrate.go` встраивает `migrations/*.sql` в бинарник. При старте API он берёт
транзакционную advisory-блокировку, выполняет новые файлы по имени и записывает
их в `schema_migrations`. Повторный запуск не применяет их заново; при ошибке
транзакция откатывается. Применённый файл не редактируют: добавляют следующий.

`001_init.sql` создаёт users и tasks, внешний ключ владельца, уникальный логин,
проверки статуса/формата и индекс неопубликованных задач. Запросы параметризованы.
Пул PostgreSQL ограничен 10 соединениями; запросы имеют таймауты.

```text
main.go                 соединяет зависимости и запускает API
http.go / image.go      маршруты, multipart, HTTP-коды, выдача файлов
commit.go               проверяет callback и завершает задачу
auth.go / auth_http.go  пароли, регистрация/вход, middleware
sessions.go            Redis, хеш ключа сессии и TTL
task.go                задача, проверка владельца, диспетчер outbox
store.go               SQL для пользователей, задач и публикации
migrate.go             встроенные SQL-миграции
migrations/001_init.sql схема PostgreSQL
metrics.go             HTTP-счётчики и время запросов
internal/jobs/         общие сообщения, лимиты, пути, Kafka writer
processor/main.go      чтение Kafka, callback, подтверждение offset
processor/filters.go   декодирование и четыре фильтра
processor/metrics.go   время и результат попыток обработки
monitoring/            Prometheus, provisioning и дашборд Grafana
docs/openapi.yaml      актуальный API-контракт
scripts/setup_env.py   недостающие локальные секреты
Dockerfile             образ API
processor/Dockerfile   образ обработчика
compose.yaml           зависимости, тома и локальные порты
tests/                 сквозные проверки на работающем стеке
Makefile / .github/    команды и workflow CI
```

Два бинарника используют один небольшой пакет `internal/jobs`. Остальные файлы
API остаются в `package main`. Интерфейсы описывают операции хранилищ, без
универсальных слоёв и ORM. Пароли, токены и байты картинок в метрики не попадают.

## Мониторинг

`image_processing_total{filter,status}` считает попытки обработки: success/failed.
`image_processing_duration_seconds{filter}` измеряет декодирование, фильтр и запись,
исключая ожидание очереди и callback. Повторная доставка даёт новую попытку.
`image_api_requests_total{method,route,status}` и
`image_api_request_duration_seconds{method,route}` показывают HTTP-нагрузку,
ошибки и задержки. Route — шаблон без ID, поэтому число временных рядов ограничено.
`/healthz` и `/metrics` исключены из счётчиков пользовательских запросов.

Grafana показывает доступность двух целей, попытки/ошибки, распределение по фильтрам,
p95 обработки, HTTP RPS, 5xx и p95 запросов. `up=1` означает доступный endpoint
метрик, а не гарантированно работающую очередь. После рестарта процесса счётчики
обнуляются, `rate` учитывает сброс. p95 по коротким учебным сериям приблизителен.
Оповещения и отдельные экспортеры инфраструктуры не настраивались.

## Проверка и CI

```sh
go build ./...
go vet ./...
python tests/smoke.py --restart-processor
python tests/persistence.py
```

Smoke проверяет четыре фильтра, PNG/JPEG, права владельца, лимиты, повреждённое
изображение, повторный callback и очередь при остановленном processor.
Persistence проверяет сохранность после рестартов API/БД/Redis, TTL, ответы при
отказах, outbox при выключенной Kafka и сбор метрик. Эти команды временно
останавливают сервисы; используйте их на локальном учебном стеке.

Локально успешно выполнены сборка обоих Docker-образов, `go build`, `go vet`,
71 HTTP-проверка и весь сценарий persistence с отказами, рестартами и мониторингом.

Файл `.github/workflows/ci.yml` внутри `hw3` сохранён как шаблон CI для
самостоятельного репозитория проекта. GitHub не запускает workflow из вложенной
папки `hw3/.github/workflows`. Здесь используются локальные команды выше;
корневая конфигурация репозитория и остальные задания не изменялись.

## Границы проекта

Один API, один processor и один брокер; общий файловый том рассчитан на один
Docker-хост. TLS, S3, logout, удаление пользователей/картинок, квоты, автоматическая
очистка файлов и резервное копирование не реализованы. При сбое записи SQL после
сохранения картинки может остаться файл без записи; при неоднозначном ответе БД
он намеренно не удаляется. Повтор POST после потери ответа может создать ещё одну
задачу: ключа идемпотентности загрузки нет. Для нормальных рестартов сохранности
достаточно томов; отказ диска и удаление томов требуют восстановления из бэкапа.
